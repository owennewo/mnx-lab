**Implementation loop. Agent assessment, application `666ea4ee`, 2026-09-24.** Six unchanged originals from the pinned 183-fixture W3C/LilyPond suite were opened in both desktop shells. The [machine report](../harness/reports/musicxml-tuplet-assessment.json) records 65 stable feature IDs, 194 source note variants, 56 source tuplet-group variants, 18 source marking/dynamic controls and 130 feature × shell × Notation rows: 58 correct, 66 incorrect, 2 partial, 4 missing. ## Evidence and method

The [pinned manifest](../converters/fixtures/musicxml-suite/manifest.json) gives the original paths, descriptions, SHA-256 values and suite revision. The [verifier](../harness/verify/musicxml-tuplet-assessment.py) derives note and group IDs such as `23b-Tuplets-Styles/p01/m02/t04` from original XML. It pairs numbered start/stop markers, inventories the three marker-free `23f` passages using the manifest's described boundaries, compares every source pitch and written value with browser-imported MNX, checks performed bar spans, and verifies the [retained capture hashes](../harness/fixtures/musicxml-tuplet-evidence/manifest.json). Each shell's imported MNX, observation JSON, full Notation SVG and PNG are retained. Source and imported documents match between shells.

Both shells used Chrome 153.0.8010.36 at 1440×1000, device scale 1, staff scale 1 and density 2. Settings showed clefs and time signatures. These sources have no lyrics; the Current verse setting cannot hide a tested feature. All six scores fit one viewport in each shell, with no horizontal or vertical score scroll remainder. The PNGs were visually inspected after checking those settings and the captured scroll dimensions. Every Studio XML version was made current and editable via Versions. That workflow is a display prerequisite, not an authoring or GP storage pass. No original declares strings, so Tab/Both are inapplicable.

Reproduce in an isolated worktree after `npm ci` and `npm run build`:

~~~sh
MUSICXML_CAPTURE_FILTER='^23[a-f]-' MUSICXML_CAPTURE_TIME_SIGNATURES=show MUSICXML_CAPTURE_DIR=/tmp/mnx-musicxml-tuplets-workbench node harness/verify/musicxml-editor-capture.mjs
MUSICXML_CAPTURE_SHELL=studio MUSICXML_CAPTURE_FILTER='^23[a-f]-' MUSICXML_CAPTURE_TIME_SIGNATURES=show MUSICXML_CAPTURE_DIR=/tmp/mnx-musicxml-tuplets-studio node harness/verify/musicxml-editor-capture.mjs
python3 harness/verify/musicxml-tuplet-assessment.py
~~~

The commands create fresh `/tmp` captures; the verifier checks the committed copies. The official MusicXML [`<tuplet>` definition](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/tuplet/) separates graphical display from sounding [`<time-modification>`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/time-modification/). [`<tuplet-actual>`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/tuplet-actual/) can override displayed numbers and note types. Published MNX [tuplets](../spec/mnx-schema.json) have `inner`/`outer`, `bracket`, `orient`, `showNumber` and `showValue`; the importer currently carries only the arithmetic sides. The existing notation emitter prints the inner count or suppresses it, and does not yet honor all published display choices.
